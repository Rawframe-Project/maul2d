# Release

Releases are made by release-please from the conventional commit titles on `main`. Versions follow Semantic Versioning within major version 1: a feature makes a minor release and a fix a patch release. There is no 2.0.0. A change that would break a program built against 1.y is designed to be additive or does not land, and the title check refuses a `!` title or a `BREAKING CHANGE:` footer. A change that gives existing inputs a different result is titled `feat`, or `fix` when it corrects a result the documentation already promised, and its pull request body and the release notes say what changes. maul2d adds one rule of its own, in the notes below: a release that changes results is always a minor release. Tags are `vX.Y.Z`.

## Steps

1. release-please keeps a draft pull request titled `chore: release X.Y.Z` open. It moves the version between the markers in `include/maul2d/base.h`, where CMake and `M2_ABI_VERSION` read it, updates `.release-please-manifest.json`, and adds an entry to `CHANGELOG.md` from the `feat`, `fix` and `perf` titles.
2. Rewrite that entry in user language before merging: what changed for someone using the library, grouped as Added, Changed, Fixed, Removed and Security. Leave out refactors, tests, CI and documentation. Name every change of results, with the golden lines it moves, and every change of the snapshot and tape formats, since games compare hashes across machines and a minor release refuses the snapshots and tapes of another.
3. Check that the `required` CI job passed on the release pull request on every cell.
4. Mark the pull request ready and merge it. release-please tags the merge commit and publishes the GitHub release with the changelog entry as its notes. The Pages workflow publishes the documentation and the testbed from `main`.
5. `.github/workflows/release.yml` then builds the source archive, writes `SHA256SUMS` and an SPDX SBOM, attests where they were built, and attaches them to the release. Like every Maul library, maul2d ships as source; packages for vcpkg and Conan are a family decision of their own. Check that the assets are there; a user verifies a download with `sha256sum -c --ignore-missing SHA256SUMS` and `gh attestation verify <file> -R Rawframe-Project/maul2d`.

## Notes

- A version that is not the next one by the commit titles is set with a `Release-As: X.Y.Z` footer in the commit that should produce it.
- The binary interface is the major and minor version: `M2_ABI_VERSION` encodes them, the shared library's `SOVERSION` is `1.Y`, and the CMake package accepts any later 1.y (SameMajorVersion). A program built against 1.y builds against a later 1.z and means the same; it links against the 1.y library it was built for, since a minor release may add a field at the end of a def.
- The shared family files must match their canonical copies in the organization's `.github` repository before a release.
- A release whose `test/hashes.txt` differs from the last tag's is a minor release, even when the change behind it is a `fix`. This is stricter than the family standard, which lets a `fix` ship in a patch, and it keeps the replay promise exact. A patch release's `M2_ABI_VERSION` is its minor version's, so it reads the snapshots and tapes of the release before it, and a tape replays its calls on the reader's step code: a moved golden line would replay an old tape onto other bits instead of refusing it. A minor release carries a new `M2_ABI_VERSION`, so every snapshot and tape still replays onto the same bits or is refused with `m2_errorVersion`.
- The format versions move once per release, not once per pull request. The first pull request in a release that changes the snapshot's bytes bumps `M2_SNAPSHOT_VERSION`, and the first that changes the bytes of an existing tape record bumps `M2_JOURNAL_VERSION`. Later pull requests in the same release keep those numbers. A record that a release only adds, a new operation or parameter channel, leaves `M2_JOURNAL_VERSION` as it is: the reader checks the tape's `M2_ABI_VERSION`, which differs for every minor, before it reads any record.
- How the minor is cut: a `feat` makes the next release a minor by itself. A `fix` that moves a line of `test/hashes.txt` ends its pull request body with `Release-As: X.Y.0`, where X.Y.0 is the minor after the version in `.release-please-manifest.json` on `main`. The pull request's author adds the footer, and the squash commit carries it to release-please. `tools/check_patch_results.py`, run by CI on every pull request, fails the release pull request when its version is a patch of the last tag and `test/hashes.txt` differs from the tag's. If that happens, the curator opens a pull request whose body ends with the same footer, and release-please then proposes the minor.
- When a release exists without its files (the assets job failed, or the release was made by hand because release-please could not make it), run the release workflow by hand from `main` with the release's tag, `gh workflow run release.yml --ref main -f tag=vX.Y.Z`. It builds the files from the commit the tag names, as checked when the run starts, and attaches them. It refuses a name that is not `vX.Y.Z`, a tag other than the one release-please creates in the same run, a tag on a commit `main` does not hold, and a release that already has files: a published file is never replaced. A run that failed after attaching some files is re-run only after deleting those files from the release by hand (`gh release delete-asset vX.Y.Z <file>`).
- Tags are never deleted or moved. A broken release is fixed by the next one.
